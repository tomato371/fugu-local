01 — Overview

全体像

fugu-nim は 4 つの層でできています。判定（Conductor）、 解法（SC 投票 / MoA 合議）、検証（PoT・Critic・裁定）、 通信（NIM 送信層）。

入口はひとつです。質問は必ず Conductor を通り、そこで task_type（math / mcq / code / knowledge / writing / chat）と mode（single / moa）が JSON スキーマで拘束された形で決まります。 以降の経路はこの判定に従います。

02 — Model lineup

モデル構成

提案者は アーキテクチャも学習系譜も異なる 4 モデルで構成します。 同じモデルを 4 回呼ぶのではありません。同じモデルの複数サンプルは同じ誤りをするため、 多数決が機能するのは系譜が異なるときだけです。

各提案者にはペルソナが与えられ、システムプロンプトで役割が固定されます。 これは擬人化の趣味ではなく、同じ問題を異なる観点から攻めさせて誤りの相関を下げるための機構です。

可用性プローブ — 起動のたびに布陣を組み直す

NIM ではモデル単位で混雑 429 や、カタログ掲載のまま 404 が返ることがあり、時間帯で回復します。 そのため apply_nim_profile() は起動時に max_tokens=4 の軽量プローブを打ち、 その時点で使える最強の布陣を組みます。

重要なのは切り分けです。不安定なモデル（deepseek-v4-pro）は 提案者としては残す——落ちても MoA は 3 体で縮退して耐えます。 しかし投票系統と裁定からは外します——ここが落ちると精度が直接壊れるからです。 「壊れても平気な場所」と「壊れたら終わる場所」を区別して配置しています。

この設計の副作用として、再現実行が常に同じモデル構成になる保証はありません。 実行時のログに [setup] nim probe: として選定結果が出力されます。

03 — Routing

経路とルーティング

Conductor の出力は自由記述ではなく、enum で値域まで拘束した JSON スキーマに従います。 自由な JSON にすると mode に "mathematical_proof" のような存在しない値を捏造するため、 スキーマで縛ることが要点になっています。 

{
  "mode":               // enum: "single" | "moa"
  "task_type":          // enum: "math"|"code"|"mcq"|"knowledge"|"writing"|"chat"
  "selected_proposers": // ["Proposer A", ...]
  "rounds":             // 1..4
  "search_required":    // 時事・価格・バージョン等なら true
  "use_image_generation", "image_only", "make_pptx",
  "reason"
}

精度優先の原則がプロンプトに書かれている

Conductor のシステムプロンプトには、single を許可する範囲が明示的に絞られています。 コード生成・数学・証明・論理パズル・多段推論・比較要約翻訳は、 簡単そうに見えても必ず合議。迷ったら合議。 これは「単一モデルが見落とす誤りを相互チェックで潰す」という設計方針を、 実行時の判定に落とし込んだものです。

さらに LLM の判定を鵜呑みにせず、正規表現によるガードレールが後段で補正します （_apply_accuracy_guardrails / _apply_tasktype_guardrails / _apply_routing_guardrails）。判定モデルが軽量な 8B であるぶん、 決定論的な安全網を重ねる構成です。

04 — Voting engine

自己一貫性投票エンジン

数学・選択式のように答えが一意に定まる問題は、文章を統合するのではなく投票で決めます。 投票は打ち切りではなく収束するまで票を足す方式です。

PoT — 唯一の機械的な票

Program-of-Thought は Python コードを生成し、ローカルで実行してその出力を 1 票として扱います。 自然言語の推論は計算を間違えますが、Python の算術は間違えません。

クラウド構成でもコード実行はローカルの subprocess で行われます。 つまり PoT 票はバックエンドに依存しない純粋な追加であり、これが機械検証票の価値です。

並列でも結果は決定的

クラウドではモデルのロードが存在しないため、バッチ内サンプリングを ThreadPoolExecutor（4 ワーカー）で並列化しています。

ただし結果の回収は投入順に固定しています。 並列化しても票の並び・PoT の位置・ログの順序が変わらないため、 逐次実行との比較可能性が保たれます。

05 — Deliberation

MoA 合議

答えが一意に定まらない問題——解説・文章・設計・コード——は投票できません。 こちらは提案 → 統合 → 批評のラウンドで進みます。

  1. 提案：選抜された 3〜4 体の Proposer が並列に独立解答を生成する（temp 0.7、多様性優先）。
  2. 統合：Aggregator が全提案を読み、1 つの回答へ統合する（temp 0.5）。
  3. 批評：Critic が「正しく・完全で・筋が通っているか」を JSON で判定。保守的に運用し、明確な問題があるときだけ ok=false。
  4. 第二意見：Conductor と別系譜のモデルが独立にチェックする。
  5. 反復：不十分なら統合結果を土台に次ラウンドへ（最大 4）。

次ラウンドへ持ち越す土台からは思考ブロックを除去しています。 除去しないと、モデルの内部思考が「パネルのドラフト回答」として次の提案者に提示され、 改善を誤誘導するうえ、文脈長を圧迫して肝心の質問文が切り詰められます。

06 — Transport

通信層 — クラウド越しに長時間推論を通す

ここは実装上もっとも作り込まれた部分です。30 分以上かかる推論を、 レート制限のある無料 API 越しに、途中で切られずに完走させる必要があります。

設計契約はひとつだけ：送信層は例外を投げず、失敗を __ERROR__: で始まる文字列として返す。 これはローカル版の ask() と同一の契約で、だからこそ呼び出し 13 箇所を 一切変更せずにバックエンドを差し替えられます。失敗が文字列で返るため、 投票側は無効票として自然に扱えます。

実測から入った 3 つの防御

ストリーミング必須。 非ストリーミングでは、思考モデルの長い生成中に NIM のゲートウェイが待ちきれず HTTP 504 を返します（550B モデル × AIME 難問で再現）。 SSE でチャンクを受け続けていればゲートウェイは切りません。

指数バックオフ。 429 に対する 10 秒固定の再送は、 ハンマリングによってスロットルを永続化させました（自己増幅する 429 の嵐）。 現在は 20·2ⁿ⁻¹ 秒・上限 120 秒。

モデル別クールダウン。 429 を踏んだモデルは一定時間送信を控えますが、 待機はセマフォを取得する前に行います。グローバルに待つと、 1 モデルの混雑で全系統が止まってしまいます。

2026-08-06 追記 — 積み上げは sc7 で止まっている

sc8 以降の 3 構成（境界監査・挑戦者制度・機械検証官）はいずれも 1 問も救えていません。 設計上の欠陥ではなく、機構が動く前に材料が枯れるのが直接の原因でした—— 機械検証官は 3 モデルすべてが検証プログラムの生成に失敗して裁定に至らず、 境界監査は共有された誤りそのものを検出できませんでした。

同時期に測った統合 MoA（u@nim）も、MATH-500 42 問で 既存 42/42 に対し 41/42・コスト約 7 倍という結果です。 集約側の設計はここで一度飽和したと考えるのが素直で、 次に効くのは新しい集約理論ではなく、下の「抽出失敗」の修復のほうです。

いま最大のボトルネック — 4 系統が実質 2 系統に溶けている

失敗問題を全構成横断で集計したところ、抽出失敗（思考が max_tokens を 食い尽くして本文ゼロ／混雑時の空応答／PoT の実行失敗）が モデルによって極端に偏っていました。

この欠落は集約の外側で起きるため、どれだけ集約を賢くしても取り返せません。 「4 系統で投票している」という前提自体が、難問では成り立っていませんでした。

この表が示していること

計算量を積む方向（sc3〜sc4）は 93% 付近で飽和します。 票を 32 に増やし思考を 32k から始めても、1 問救うのに 1,149 リクエスト——sc2 の 11 倍です。 DeepConf に至っては 0 問でした。

飽和の先を動かしたのは集約設計の変更でした。 SC-Court（候補を対審にかける）と S3C（解法戦略を強制的に散らす）は、 計算量ではなくサンプル間の誤り相関を壊しにいく手法で、 140〜247 リクエストで 1 問ずつ救っています。

温度 0.7 で何度サンプリングしても、全系統が同じ筋読みをしていれば票は同じ誤りに揃います。 多数決が直せるのは確率的な誤りだけで、相関した誤りは増幅されます。 S3C はこの前提そのものに介入する手法です。

DeepConf をなぜ残しているか

DeepConf（低自信トレースを除外した自信度加重多数決）は論文どおりに実装されています—— スライディング窓 1024、最悪 10% 窓群の平均を自信度とし、下位 50% を投票前に除外。 「トレース全体の平均ではなく最悪区間を見る」という論文の要点も実装済みです。

それでも実測は 0/5 でした。異なるモデルは logprob のスケールが揃わないため、 自信度を横断比較すると誤った重み付けになります。コードには 【実測 2026-08-05: 0/5 で有害と結論。記録用に構成は残す】 と書かれたまま保存されています。同じ手法を将来もう一度実装しないためです。

設定の指針

速度が要るなら SC_MAX を下げます。実測では 100 リクエストを超えた問題群の 正答率は 48% であり、後半のサンプリングは期待値が低下します。

安定性が要るなら NIM_MAX_CONCURRENCY を下げます。 4 は約 40 RPM の制限下で 429 を踏みすぎない値として実測で決めたものです。

機密データを扱うなら FUGU_BACKEND=ollama（既定）を使い、 CODE_EXECUTION = False で PoT のローカル実行も無効化してください。
