What it is

一行で言うと

Quorum は、複数の異なる大規模言語モデルに同じ問題を独立に解かせ、投票と対審で 1 つの答えに収束させるオーケストレータです。 単一モデルへの問い合わせを置き換えるものではなく、単一モデルでは届かない精度に、時間と引き換えに到達するための層です。 名前の Quorum（定足数）は、複数モデルの独立した投票が定足数に達してはじめて答えを採択する、というこの設計そのものを指しています。

中核にあるのは 1 つの主張です。誤りが相関していない複数のモデルを合議させれば、個々のモデルより正確になる。 これはアンサンブル学習の古典的な原理ですが、言語モデルに適用するとき難しいのは「誤りを相関させないこと」の方です。 Quorum の設計の大半は、この相関を壊すために費やされています。

Design principles

3 つの設計原則

Quorum は 8GB VRAM のノート PC 向けに設計された fugu_local の派生です。 制約から出発したことが、そのまま設計原則になっています。

01

誤りを相関させない

同じモデルの複数サンプルは同じ誤りをする。だから提案者はアーキテクチャも学習データも異なる 4 モデルを使い、 さらに解法戦略を明示的に散らす。多数決が意味を持つのは、票が独立しているときだけ。

02

律速は検証器にある

改善ループは「生成 → 評価 → 選択」で回る。評価が壊れていれば、どれだけ良い生成をしても選択が誤る。 コミット履歴の相当部分は、表記ゆれの吸収や無効票の判定といった採点側の修正に費やされている。

03

失敗は消さず記録する

効かなかった手法をコードから削除しない。DeepConf は正しく実装した上で 0/5 と測られ、 「異種混成では有害」という注記とともに構成ごと保存されている。負の結果は再実装を防ぐ資産である。

集約をどこまで賢くできるか — 5 つの理論と、その実測

限界 4 番（計算量を積んでも 93% で頭打ち）に対して、票を増やす以外の手を 5 つ設計し、 すべて実装して実際の問題に投入しました。以下は成功した 2 つと、失敗した 3 つの記録です。 効かなかった手法も構成ごと残してあります（SC_* フラグは既定 False）。

出発点は、既存研究の移植が失敗したことでした。Meta の DeepConf（生成トークンの logprobs から「自信度」を測り、確信度で重み付けした多数決に置き換える手法）を実装して 限界 5 問に投入したところ 0/5。それどころか、全 5 問で 「生の多数決の勝者」を「少数票だが自信のある誤答」へ書き換えていました。 ある問題では正解 248（4 票）を 1 票の 221 に上書きして取り逃しています。 原因は明快で、論文が前提とする単一モデルの密な logprobs と違い、 異種モデルを混ぜると自信度の尺度がモデル間で揃わない——過信するモデルが常に勝ちます。 ここから、生成側の内部信号ではなく検証側の信号を使う方向に切り替えました。

Known limitations

わかっていないこと、うまくいかないこと

導入判断のためには、成功例より制約のほうが役に立ちます。現時点で確認されている限界を、 測定値とともに列挙します。ここに書かれていない性能は、測っていないものと考えてください。

1. 遅い。対話用途には使えない

HumanEval 30 問の所要時間は中央値 317 秒（5.3 分）、最長 2,114 秒。 60 秒以内に終わった問題は 30 問中 0 問でした。これは不具合ではなく「精度優先・時間は無制限」という設計選択の帰結です。 エディタ補完やチャット相談の代替にはなりません。

2. 標本が小さい

AIME は各 30 問、MATH-500 は 50 問、HumanEval は 30 問。 1 問の差が 2〜3.3 ポイントに相当します。 「AIME26 で基準モデルを上回った」は 1 問差であり、統計的に有意な差の主張ではありません。 正確には「同水準に到達し、単価を 0 円に抑えた」です。

3. 中難度の評価は、採点器の問題だった2026-08-06 改訂

当初ここには「MATH-500 で 43/50（86%）、中難度を確実に落とさない能力は明確に劣る」と書いていました。 これは誤りでした。再採点すると 49/50（98%）で、基準モデル 99/100（99%）と実質同点です。 落ちていた 6 問はすべて表記ゆれによる誤判定で、解答自体は合っていました。

残る限界として正しいのは、採点器そのものの信頼性のほうです。 いまも式中の空白（-13x + 3 と -13x+3）は同値と判定されません。 自作ハーネスで自己採点している以上、スコアの一部は常に採点器の関数である という前提で読む必要があります（限界 5 番）。

4. 計算量を積んでも 93% 付近で頭打ちになる

票数を 32、思考トークンを 32k まで増やした構成に 2,445 リクエスト・約 34 時間を投じて、 救えた問題は 1 問でした。残る誤りは確率的ではなく系統的——複数モデルが同じ仕様誤読をする種類——であり、 多数決では直りません。この飽和を超えたのは計算量ではなく集約設計の変更でした。

5. 採点は自作ハーネスによる自己採点

すべてのスコアは同梱の bench_fugu.py による採点です。第三者検証は受けていません。 2026-08-04 に表記ゆれ 4 種を吸収する採点修正を入れており、そのぶんスコアが動いています （過去分は regrade ツールで再採点済み）。採点器の改善分と手法の改善分は分離されていません。

6. 未測定・未解決の領域

GPQA は実行が rc=1 で失敗しており未取得です。長文脈・マルチターン対話・ エージェント的なツール使用は測定していません。AIME 90 問のうち 3 問 （aime24-2024-I-12, aime24-2024-II-15, aime25-13）は 全 9 構成が解けていません。

7. 外部サービスの可用性に依存する

NIM のモデルは時間帯によりモデル単位で 429（混雑）や 404（カタログ掲載のまま利用不可）を返します。 起動時に可用性をプローブして布陣を組み替える実装が入っていますが、 再現実行が常に同じモデル構成になる保証はありません。

合成性の導入 — 実装して、測った

上の限界 4 番（計算量を積んでも 93% で頭打ち）に対する答えとして計画していた改修です。 2026-08-05 に実装を完了し、翌日から測定に入りました。 以下は動機（当時の設計判断）と、実際に測って出た数字です。

この系を回路として見ると、置換不変性（多数決）と時間不変性（合議の反復）は使っている一方、 局所性と合成性を一度も使っていないことがわかります。 すべてのサンプルが問題を丸ごと解くため、5 段の推論なら各段 0.8 の正答率が 0.8⁵ ≈ 0.33 に落ちる——誤りが乗算で効きます。 全系統が同じ段で転べば票は揃って間違うので、票を増やしても直りません。

そこで CNN のエッセンス——局所受容野・重み共有・階層的プーリング・因果性——を導入し、 問題を段に分けて段ごとに投票する構成（u@nim）を実装しました。 構造としては TCN（時間畳み込みネットワーク）と同型で、 軸が「時刻」ではなく「推論の段」に変わったものです。

同時に、task_type による経路分岐も廃止しました。 従来は Conductor が「数学か否か」を予測して投票経路と合議経路に振り分けていましたが、 この判定は 6 ベンチのうち 1 つでしか動いておらず、外すと投票エンジンを丸ごと失う。 しかし 2 つの経路は集約方法が違うだけなので、 提案を生成した後に「比較可能な結論が抽出できたか」を見れば済みます—— 入力の分類ではなく、出力の性質で決める（遅延束縛）。 副産物として、コード生成にも投票が使えるようになりました （実装が違っても同じ入力に同じ出力を返すなら等価という振る舞いハッシュをキーにする）。

測定結果 — 精度は上回らず、コストは 7 倍（2026-08-06 途中経過）

MATH-500（42 問・両側に同じ正規化採点を適用）: 既存 sc@nim 42/42 に対し 統合版 41/42。 リクエストは 1 問あたり 7.7 → 55.2 と約 7 倍に増えています。 AIME25（12 問）は 8/12 で同点ですが、内訳は「既存が落としていた 3 問を救済し、 既存が解けていた 3 問を新たに落とした」入れ替わりでした。

回帰した 3 問はいずれもわずか 14〜22 リクエストで早々に確定して誤答しています。 段ごとの早期確定とソフトプーリングへの落下が、期待した合成性の利得より先に副作用として出ました。

さらに深掘りの暴走を確認しました。AIME24 の 1 問目は 8 段に分解された後、 第 4 段と第 6 段がそれぞれ 8 副段・7 副段へ再分解され、18 時間経っても 1 問が終わりませんでした。 階層再分解に予算上限を設けていないことが原因です（測定枠を空けるため打ち切り）。

この改修は「スコア向上を完了条件に含めない」という約束のもとで実施したものです。 現時点の答えは「精度では上回らなかった」。構成は削除せず、回帰リストとともに記録します。

先行した事前診断は「中止」を出していた

実装に先立ち、既存の失敗トレースだけを機械集計する診断（API 呼び出しゼロ）を回しています。 判定は中止でした——失敗の主因は生成側の段構造ではなく 集約と票の枯渇の側にあり、 「正解が票のどこにも現れない」問題は未解決 3 問中 1 問にとどまる一方、 票が枯渇していた記録が失敗全体の 38% を占めていたためです。 段別に投票しようにも、投票する票がありません。

寄与はフラグで切り分けます。 段階に分けない代わりに、 実装後に leave-one-out のアブレーションを 1 回回します。 切り分けの手段は実装順序ではなくフラグである、という設計です。

スコア向上は完了条件に含めません。 下回った場合は、その事実と 回帰リストを報告することが完了条件です。 効かなかった手法を消さずに記録するのは、この系の既定の作法です。

Fit

向いている用途、向いていない用途

向いている

  • +夜間バッチでの難問一括処理。待ち時間が問題にならない場面
  • +数分〜数十分かける価値のある単発の難問（証明・アルゴリズム設計）
  • +複数モデルの解法を並べて比較したい研究・教育用途
  • +オーケストレーション手法そのものの実験基盤。構成を差し替えて効果を測る
  • +API 課金を避けたい環境（無料枠・ローカル両対応）

向いていない

  • −エディタ補完・対話的なコーディング支援。中央値 5 分は待てない
  • −ユーザー向けのリアルタイム応答が要るプロダクト
  • −SLA・可用性保証が必要な本番系。外部無料枠に依存している
  • −大量の平易な問い合わせ。1 問に平均 3.7〜62 リクエストを消費する
  • −機密データの処理。クラウド構成では外部 API へ本文が送信される

Reproducibility

検証のしかた

主張を信じる必要はありません。同じ手順で再測定できます。 本体は Python 標準ライブラリのみで動作し、外部パッケージのインストールを必要としません （Office ファイルの読み込みなど一部の任意機能を除く）。 

# 1. NIM の API キーを設定（build.nvidia.com で無料発行）
$env:NVIDIA_API_KEY = "nvapi-..."
$env:FUGU_BACKEND  = "nim"

# 2. 対話 / 一問一答
python fugu_local.py "次の方程式を解け ..."

# 3. ベンチマーク再現（1問1行の JSONL が追記される）
python bench_fugu.py run --dataset aime26 --config sc@nim
python bench_fugu.py run --dataset humaneval --config coder@nim --limit 30

# 4. 生成物
#   fugu_bench/results/<dataset>__<config>.jsonl
#     → id / correct / got / expected / seconds / nim_requests / answer_text
#   fugu_bench/nim_usage.json  → 累計リクエスト数（プロセス跨ぎ）

結果ファイルには回答全文が残ります

各行の answer_text には、そのモデルが実際に生成した解答が丸ごと入っています。 correct の判定に納得できない場合、生成物そのものを読んで検証できます。 seconds と nim_requests により、精度と計算量の関係も後から再構成できます。

Data & compliance

データの扱いについて

研究用途で使っていただくうえで、データがどこへ行くかは明確にしておく必要があります。

送信されるもの

クラウド構成（FUGU_BACKEND=nim）では、質問文・添付文書から抽出したテキスト・ 検索結果が NVIDIA NIM の API へ送信されます。機密情報を扱う場合はローカル構成 （Ollama）を使用してください。ローカル構成では外部への送信は発生しません （Web 検索機能を明示的に有効にした場合を除く）。

収集しないもの

テレメトリ、利用統計、エラー報告の外部送信は実装されていません。 nim_usage.json にリクエスト数を記録しますが、これはローカルの予算管理用で、外部へは送られません。

学習データの方針

自己改善用のトラジェクトリ収集機構（fugu_selfimprove）には コンプライアンスゲートが最初の実装から組み込まれています。 商用 LLM の出力を教師データとする蒸留は各社の利用規約で禁止されているため、 教師データはローカル生成のみに限定され、これはコードレベルで強制されています。

コード実行について

Program-of-Thought（PoT）機能は、モデルが生成した Python コードをローカルで実行します。 タイムアウト（既定 90 秒）とサンドボックス設定がありますが、 信頼できない入力を扱う場合は CODE_EXECUTION = False で無効化してください。
