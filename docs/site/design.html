訂正 — 199/210 は単一システムの成績ではなかった

何が間違っていたか

本サイトはこれまで 199/210 を「fugu-nim の成績」として掲げ、 基準モデルの 199.5/210 と同点だと述べてきました。これは誤りです。

199/210 は 20 以上の構成の和集合——「どれか 1 つの構成で解けたら正解」 として数えた値でした。一方、比較対象の 199.5/210 は単一モデルの成績です。 性質の違うものを並べていました。

単一構成の最良合計は 187/210 です。 したがって公平な比較は 187 対 199.5 で、12.5 問の差があります。

なぜこれが「オラクル」なのか

差の 12 問は「sc@nim で落ちた問題に別構成を当て、当たったら正解と数えた」結果です。 どの構成を使うかを、正解を見てから選んでいます。 実行時にはその選択ができないので、199 は到達可能な成績ではなく上限です。

さらに 128 問は 1 つの構成でしか解けていません。 構成選択が成績を支配しており、それを正解なしに当てる機構は実装されていません。

なお AIME25/26 の差の一部は「429 エラーの嵐で票が枯渇した問題の再測定」で、 最初の測定が無効だった分です。ただし修正後に全問を測り直したわけではなく 失敗した問題だけを再走させているので、これも汚染されています。

「40% → 97%」も同じ問題を抱えている

分母の 40% は think@nim の 2/5（n=5）、 分子の 97% は和集合です。正直な数字は 単発 2/5 に対し sc@nim 単一構成で 25/30（83%）。 方向は明確ですが、+57 ポイントという値は過大で、実際は +43 程度、 しかも分母の標本が 5 問しかありません。

さらに、この差には「異種モデルを混ぜた効果」と「単に生成回数を増やした効果」が 分離されずに含まれています。多様性の寄与は未測定です。

Line closed

検証機構への投資を止める — 2 回の失敗で条件が満たされた

機械検証官（独立生成したプログラムの実行結果を最終裁定にする機構）は、 2 回の実測で結論が出ました。

1 回目（sc10b）：プログラムが正解 385 を計算して印字したのに、 「2 本以上の一致」規則が棄権を選び、言語側の誤答 24 が確定しました。 規則が正解を捨てた——そう解釈して規則を修正しました。

2 回目（sc11・修正版）：生成失敗の補充とコード審査を実装して再挑戦。 機構は設計どおり動作しました（審査は 3 名とも発火）。 しかし今回はどのプログラムも 385 を出しませんでした—— 出力は 1 / 99 / 168 で、審査も割れ、最終回答は 16（正解 385）。

この 2 回が意味すること

385 の出現は n=1 の観測であり、再現しませんでした。 したがって「集約規則が正解を捨てていた」という診断は、正しくはあっても 主因ではありません。規則を直しても、材料のほうが安定して出てこない。

この問題（aime24-I-12）は 5 回の独立試行すべてが 384 に到達する 共有されたオフバイワンであり、裁判官にも監査人にも、 そして機械検証にも安定しては見えませんでした。 これは検証機構の問題ではなく、生成側の問題です。

撤退条件は事前に「385 を出力したプログラムが存在しなければ投資を止める」と 決めてありました。その条件が満たされたので止めます。 sc10 / sc11 の構成はコードから削除せず、この結果とともに残します。

Ranked actions

次にやること — 上位 4 つは新機構をひとつも足さない

以下は 8 領域の技術調査（Web 調査を含む）と、4 つの独立設計への 敵対的反証から導いた優先順位です。各項目には捨てる条件を先に固定してあります。

順序の原理は「引き算と回収が先、追加は後」です。 rank 1〜4 は一つも機構を足していません。 これが sc10 / sc11 のような「もう一段の裁定機構を積む」変更との違いです。

rank 1 — 捨てている思考テキストから答えを回収する最優先

現在の実装は SSE ストリームで delta.reasoning_content を 明示的に捨て、delta.content だけを集めています。 思考が max_tokens を食い尽くして本文がゼロになると、 すでに課金（リクエスト）を払って生成させた思考テキストを丸ごと破棄して 無効票にしています。

直し方は、思考テキストも別バッファに貯め、本文が空のときだけ 決定論的な抽出ラダー（\boxed{} の最後の出現 → 「答えは/Final Answer」マーカー → 末尾行の数式 → 最後の数値、＋単位・カンマ・全角の正規化）を掛けることです。 追加リクエストはゼロ、差分は 60 行以内、追加依存もゼロ。

期待効果：gpt-oss の有効票 93 → 200 前後（抽出失敗 78% → 50% 前後）。 票を 32 に増やす方向（1 問あたり 1,149 リクエスト）より2 桁安い。

捨てる条件：dry-run で救出成功率が 20% 未満なら放棄。 救出票を採用した結果、MATH-500 42 問で正解→不正解の反転が 2 問以上出たら即ロールバック （思考途中の暫定値を拾っている証拠）。

rank 2 — 思考予算と本文予算を分離し、max_tokens 倍増リトライを廃止する

現在は本文がゼロだと max_tokens を倍にして丸ごと再生成しています。 これは「思考をもう一度最初から全部やり直す」ので、レイテンシを確実に悪化させます。

代わりに、max_tokens の 70% を思考上限、残り 30% を本文専用として確保する 不変条件を入れ、倍増リトライは rank 1 の救出が失敗したときだけ・1 回のみに限定します。 併せて gpt-oss の reasoning_effort を high → medium に落とします。

賭けの内容を明示します：思考量を減らすと単体精度は下がる方向に働きます。 しかし現状は「賢いが票が存在しない」状態なので、 やや弱くても存在する票のほうが合議には価値がある、という判断です。

捨てる条件：有効票が 1.5 倍未満、かつ有効票の単体正答率が 10pt 以上低下したら high に戻す。 有効票が 2 倍以上なら単体正答率が 5pt 落ちても採用してよい。

rank 3 — PoT（Python 実行票）を全廃または math 限定に縮小する

自分たちの Phase 0 分析が既に結論を出しています—— 「群 A の全構成で PoT 票が正解に一致した例は 0。deepseek の PoT は大半が実行失敗」。 機構を足すのではなく引く施策であり、期待値が最も確かな種類の変更です。

判断は既存ログのオフライン集計だけで確定します（API 追加ゼロ）。 Phase 0 は未解決 3 問しか見ていないので、全 210 問で同じ集計を取り直すのが第一歩です。

捨てる条件：PoT が単独で決着させた問題が 210 問中 3 問以上あれば全廃を中止し、 math 限定＋タイムアウト 30 秒＋deepseek への割当停止に留める。0〜2 問なら全廃。

rank 4 — 待機時間に上限を入れ、待たずに別系統へ倒す

現在は 1 リクエストあたり最悪 20 分の 429 待機に、さらに 600 秒のタイムアウトが乗ります。 実測には単問 8,217 秒 / 12,886 秒 / 28,815 秒という記録があります。 1 リクエストあたりの累積待機に上限（例 180 秒）を入れ、超えたらそのモデルを 当該問題でスキップして票を他系統で埋めます。

これも測定が先です。「この呼び出しで待機に費やした秒」と 「最初の本文チャンクまでの秒」を記録し、8,217 秒の内訳が待機何 %・生成何 %かを出す。 待機が 30% 未満ならこの施策自体を捨てます。

落とし穴：LLM サーバは生成開始前にヘッダを返すため、ヘッダ受信時刻でタイムアウト判定してはいけません。 必ず最初の content チャンクの到着時刻で測ります。

rank 5〜8（rank 1〜4 の完了後にのみ着手）

rank 5 — 自己一貫性投票に早期停止を入れる。 固定 20 票をやめ、窓（3〜5 票）内が全会一致なら打ち切る。 しきい値は手書きせず、既存 210 問を較正集合とした分位点で機械的に決めます。 自分のデータ側の根拠が強い施策です——誤答「15」が 2→5→8→10 票とサンプルを増やすほど強化された記録があり、 追加サンプリングは勝者を変えていません。失うものが構造的にほぼない。

rank 6 — 日常対話用のローカル高速パスを分離する。 小型モデルを Ollama に置き、対話は既定でそこへ流す。 精度スタックに一切触れないので 210 問のスコアに影響しません。 これが重要で、脆い合議機構に手を入れずに「日常使い」を満たせます。

rank 7 — 思考オフのドラフト一致ゲートを入口に置く。 まず思考オフ・低予算のドラフトを 2 本引き、一致したら即返す。 不一致のときだけ重い経路へ。副産物として 「2 本一致した部分集合の正解率」という品質推定器が手に入り、 以降のあらゆるルーティング判断の土台になります。

rank 8 — 検証機構は撤退（上記のとおり条件成立済み）。

Explicitly rejected

やらないことと、その根拠

流行している技術ほど、この系には効かないという結果になりました。 採用しない判断にも根拠を残します——これは効かなかった構成を 削除せず注記つきで残すのと同じ作法です。

1. 構造化出力の強制（JSON mode / guided_json）を推論に適用すること

これは私が当初「抽出失敗 78%/67% の解決策」と考えていたものですが、 逆効果である証拠が出ました。

推論タスクで JSON モードを強制すると、報告されている劣化は GSM8K で 76.6% → 49.3%（GPT-3.5-Turbo）、86.5% → 23.4%（Claude-3-Haiku）。 形式の妥当性 100% と引き換えに正答率が最大 8.7pt 落ちるという追試もあります。

さらにこの系にとって致命的なのは多様性の崩壊です。 JSON で返せと指示するだけで最頻回答のシェアが 41% → 64%、 異なり回答数が 52 → 36 に減るという報告があります。 自己一貫性投票は多様性を前提にした機構なので、これは土台を壊します。

正しい適用範囲は入口判定器やルーティングのような分類的呼び出しに限ることです。 推論本体には掛けない。

2. クライアント側の制約デコーディング（Outlines / llguidance / XGrammar 等）

この領域で最も実装が充実していますが、すべて logits へのアクセスが前提です。 クラウド 4 系統は API 経由のみで、logprobs は取れてもマスクはできません。 構造的に届きません。

3. 進化的モデルマージ（および TIES / DARE / model soups）

棄却の理由は「重みが手に入らないから」ではありません。 gpt-oss は Apache-2.0、DeepSeek V4 は MIT で重み自体は入手できます。 不可能なのは次の 3 つです。

① 4 系統が共通の事前学習ベースを持たないため、 マージの前提であるタスクベクトルが定義できない。 ② V4-Pro は 1.6T 総パラメータで、空きディスク 750GB に収まらない。 ③ 仮にマージできても 8GB 1 枚では走らない。

以前このサイトおよび対話で「重みが入手不可だからマージできない」と述べましたが、 理由が不正確でした。正しくは上記 3 点です。結論（適用不可）は変わりません。

4. 合議結果を教師にした自己蒸留・自己学習

この系では特に有害です。誤答「15」がサンプルを増やすほど 2→5→8→10 票と強化された実測が、まさに合意の罠の実例です。 多数決を教師にすれば、共有された誤りが恒久化します。

5. RAG の高度化（GraphRAG / 再ランク / Agentic RAG など）

自作の RAG は既に recall@3 = 1.0 です。 挙げられる技術はすべて recall を上げるもので、定義上、効果が観測できません。 Agentic RAG 系はレイテンシが 15〜22 倍で、中央値 5.3 分の系に掛けたら破滅します。

6. 審理・監査レイヤの増設、LLM 審査員の追加

最も流行していて、この系で最も効かない方向です。 aime24-I-12 の 384 は多数決でも審理でも監査でも検出できませんでした。 文献側も、9 名の審査員パネルの実効票数が約 2.2 にしかならず、 パネル精度が独立投票の予測より 8〜22pt 低いと報告しています。

7. 学習型ルーターの新規構築（RouteLLM 等）

統一評価では上位手法でも最良単一構成に対して +4%・コスト −31.7% が天井で、 複数の手法と商用ルータは最良単一構成に負けています。 学習データも 8 万件の人間選好が前提で、210 問とは 3 桁違います。

なお「16,506 リクエスト」はラベル付き事例数ではありません。 正負のラベルが付くのは問題×構成の単位で、問題は 210・未解決は 8 しかない。 ここを取り違えると学習の設計を誤ります。

Measurement hygiene

測定の衛生 — これがないと、どの施策も効果を帰属できない

失敗を 1 つに潰さない

現在の実装は失敗をすべて __ERROR__: truncated という 1 つの状態に潰しています。 しかし中身は 4 種類あり、効く対策がそれぞれ違います。

抽出失敗の 4 分類（rank 1 と同じコミットで必ず入れる）
型状態効く対策
A思考テキストはある・本文が空（思考が予算を食い尽くした）rank 1（回収）＋ rank 2（予算分離）
B思考も本文も空（混雑・空応答）rank 4（待機上限・別系統へ）
C本文はあるがパーサが取り出せないrank 1 の抽出ラダー
DPoT のコード実行が失敗rank 3（縮小・全廃）

78% という数字が A なのか C なのかで、打つべき手がまったく変わります。 参考として、ある評価ハーネスでは抽出処理を直しただけで 特定モデルのスコアがほぼ 3 倍になった例があります。 つまり「モデルが答えていない」のではなく「取り出せていない」場合が現実にあります。

各施策の後に必ず測る 4 つ

(a) 210 問の正解数、(b) モデル別の有効票数と抽出失敗率、 (c) 1 問あたりリクエスト数、(d) 秒数の中央値と最大値。

とくに (b) が動かない改修は、この系では何も直していません。 4 系統が実質 2 系統に溶けている状態が続く限り、その上に載せた集約の実測は すべて汚染されたデータです。

評価対象から分離すべき 1 問

aime24-II-15 は問題文が参照する図がデータセットに欠落しており、 全構成が同じ誤読をしています。これは技術ではなくベンチデータの欠陥です。 直さないまま「あと 3 問」を数えると、以降のすべての A/B の分母が汚染されます。 注記つきで分離するか、図のテキスト記述を補うべきです。

Dependencies

なぜこの順序なのか

依存関係は 3 本あります。順序を守らないと、測定そのものが無効になります。

第一に、rank 1・2 が終わるまで他のあらゆる A/B は測定できません。 78%・67% が抽出失敗している状態では、どんな改修も 「有効票がそもそも存在しない」というノイズに埋もれます。 Phase 0 レポートが自分で出した優先順位の第 1 項がまさにこれで、 その後 sc10 / sc11 という別方向に 2 日投じたのが直近の経緯です。 ここに戻るのが最短路です。

第二に、早期停止（rank 5）は rank 1〜4 の後でなければ危険です。 停止則は「有効票の一致」を数えるので、抽出が壊れたまま導入すると 抽出失敗が偶然そろった時点で停止してしまいます。

第三に、ドラフトゲート（rank 7）は rank 1・2・5 すべてに依存します。 ドラフトの一致率を測るには抽出が信頼できることが前提で、 かつゲートが弾いた問題を落とす先が軽くなっていないと、 中央値は改善しても最悪ケースが変わりません。

rank 4 と rank 6 だけは完全に独立で、他のどれとも並行に着手できます。 rank 4 は測定そのものを速くするので、むしろ最初に入れると実験サイクルが縮みます。 rank 6 は精度スタックに一切触れないので、日常使いを先に満たしたいなら単独で片付けてよい。

How this was derived

この設計はどう検証されたか

単一の視点で書いた設計は、その視点の盲点をそのまま持ちます。 そこで4 つの独立した設計を、意図的に異なる前提から起こしました—— コストを唯一の軸とする案、検証可能性を唯一の軸とする案、 手書き定数の排除を軸とする案、そして引き算しか信じない案。

次に各案へ3 方向の敵対的反証をぶつけました—— 実測データとの矛盾、実行可能性、そして「6 か月後に最も後悔しているとしたら何が原因か」。 反証側には「根拠のない難癖は書くな、必ず実測に紐づけろ」と条件を課しています。

反証が実際に見つけたもの

この訂正（199 は和集合）を見つけたのは反証エージェントです。 「引き算案」の前提を検査する過程で、集計スクリプトが和集合を取っていることが指摘され、 独立に再集計して確認しました。

ほかにも、レイテンシの主因を「無料枠の奪い合い」とした案に対して 「実測は 16,506 req ÷ 4 日 = 約 2.9 req/分で、40 req/分枠の 7% しか使っていない」 という反証が出て、その案の中核が崩れました。 4 案のうち3 名の反証すべてに耐えたものは 1 つもありません。

ここに書いた rank 1〜8 は、どれか 1 つの案ではなく 4 案から反証を生き延びた要素だけを取り出したものです。
