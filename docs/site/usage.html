Choose a backend

まず、2 つのうちどちらで動かすか決める

fugu は同じオーケストレーション設計のまま、モデルの供給元だけを差し替えられる 構造になっています。切り替えは環境変数 1 つです。

クラウド（NIM）— まずはこちら

  • +GPU 不要。ノート PC でも動く
  • +100B〜550B 級のモデルを無料枠で使える
  • +本サイトの実測値はすべてこの構成
  • −約 40 リクエスト/分の制限。混雑時は待つ
  • −問題文が外部 API へ送信される

ローカル（Ollama）

  • +データが外に出ない。レート制限もない
  • +8GB VRAM から動く設計（モデルは逐次ロード）
  • −Ollama と 20B〜35B 級モデルの用意が必要
  • −8GB 環境ではモデル再ロードで大幅に遅くなる
  • −精度はクラウド構成より下がる

Quick start · cloud

クラウド構成 — 3 コマンドで動く

1. 無料の API キーを取る。 build.nvidia.com でアカウントを作り、 電話番号認証をすると nvapi- で始まるキーが発行されます。クレジットカードは不要です。

2. 環境変数を 2 つ設定して、実行する。（PowerShell の例） 

# キーとバックエンドを指定（このウィンドウ内だけ有効）
$env:NVIDIA_API_KEY = "nvapi-..."
$env:FUGU_BACKEND  = "nim"

# 質問を 1 つ投げる
python fugu_local.py "3^100 の下 3 桁を求めて"

起動時に利用可能なモデルを自動でプローブして布陣を組みます。 混雑しているモデルがあれば、その場で代替に差し替わります。 画面に出る [setup] nim probe: の行が、その日の実際の構成です。

キーを毎回打ちたくない場合は、setx NVIDIA_API_KEY "nvapi-..." で ユーザー環境変数に保存できます（新しいウィンドウから有効）。

最初の 1 問は、待つつもりで投げてください

この系は「精度優先・時間は無制限」という設計で作られています。 平易な質問なら数十秒ですが、難問では複数モデルが並列に解いて投票し、 票が割れれば追加でサンプリングします。 HumanEval 30 問の実測では中央値 5.3 分・最長 35 分でした。 エディタ補完やチャットの代わりにはなりません。

Quick start · local

ローカル構成 — Ollama を使う

FUGU_BACKEND を設定しなければ、既定でローカル（Ollama）動作になります。 Ollama を入れて、使いたいモデルを引いておきます。 

# 役割ごとに 1 体ずつ。全部揃わなくても、入っているものだけで動く
ollama pull gpt-oss:20b
ollama pull qwen3.6:35b

# そのまま起動（FUGU_BACKEND は未設定でよい）
python fugu_local.py "フェルマーの小定理を使って説明して"

導入済みモデルは起動時に自動検出され、足りない役割は入っているモデルで代替されます。 4 体すべてを揃える必要はありません。まず 1〜2 体から試せます。

8GB VRAM 環境では、モデルを 1 体ずつ入れ替えながら動きます（同時常駐しません）。 そのぶん再ロードで遅くなるため、OLLAMA_MAX_LOADED_MODELS を上げられる メモリがあるなら上げたほうが快適です。

Interfaces

4 つの入口 — 用途で選ぶ

コアは fugu_local.py ひとつで、残りはその薄いラッパです。 どれを使っても中身のオーケストレーションは同一です。

起動方法と追加依存
入口起動追加依存向く場面

おすすめの最初の一歩

まず CLI で 1 問投げて、動くことと遅さを体感してください。 気に入ったら fugu_web.py に移ると、履歴つきのチャットとして使えます。 Web UI はセッションを分けて保存できるので、テーマごとに文脈を分離できます。

Recipes

実際に役に立つ使い方

単発の質問より、ファイルを渡して結果をファイルで受け取る使い方のほうが この系の性格に合っています。拡張子から出力形式が自動で決まります。 

# 仕様書（PDF/Word）を読ませて、実装を .py で受け取る
python fugu_local.py --file spec.pdf --out impl.py

# 手元のコードを直させる（元ファイルは上書きしない）
python fugu_local.py --file buggy.py --out fixed.py

# 手元のドキュメント群を根拠にして答えさせる（RAG）
python fugu_local.py --rag ./docs "この設計の弱点は？"

# Web 検索を足す（最新情報が要るとき）
python fugu_local.py --search "NIM の無料枠の現在の制限は？"

# プロジェクトごとに会話履歴を分ける
python fugu_local.py --session ./project-a.json "前回の続きから"

# 履歴を一切使わない（単発の実験向け）
python fugu_local.py --no-history "..."

PDF の読み込みには pdfplumber、PDF での書き出しには fpdf2、 Word/Excel/PowerPoint にはそれぞれ python-docx / openpyxl / python-pptx が必要です。 入れなくても本体は動きます——テキストと Markdown だけなら追加依存はゼロです。

Reproduce

本サイトの数字を、自分で測り直す

主張を信じる必要はありません。同じハーネスが同梱されています。 まずは 5 問だけ回して、所要時間とリクエスト消費の感覚を掴むのがおすすめです。 

# 5 問だけ試す（データセットは自動ダウンロード）
python bench_fugu.py run --dataset aime26 --config sc@nim --limit 5

# 構成を変えて比べる（同じ問題に別の集約を当てる）
python bench_fugu.py run --dataset aime26 --config sc6@nim --limit 5

# 結果を集計して表示
python bench_fugu.py report

# 消費が心配なら上限を決めておく（到達で安全停止）
$env:FUGU_NIM_BUDGET = "300"

# 司令塔(Conductor)を差し替える。既定は google/gemma-4-31b-it（落ちていれば軽量機へ退避）
$env:FUGU_CONDUCTOR = "meta/llama-3.1-8b-instruct"  # 速さ優先に戻す

結果は ~/fugu_bench/results/<dataset>__<config>.jsonl に 1 問 1 行で残ります。途中で止めても、次に同じコマンドを打てば済んだ問題は 飛ばして続きから再開します。

Troubleshooting

つまずきやすいところ

応答が返らない／やたらに遅い

まず異常ではない可能性を疑ってください。難問では 1 問に数十分かかります。 画面に [SC n] の行が増えていれば進行中です。 本当に固まる場合は、ストリームが無音になってから 10 分、または全体 40 分で 自動的に打ち切って次へ進む安全装置が入っています。

429 が続く／モデルが見つからない

無料枠はモデル単位で混雑します。混雑を検知すると指数バックオフで待ち、 そのモデルだけを一時的に休ませて他の系統で続行します。 カタログに載っているのに 404 を返すモデルもあり、起動時プローブで自動的に迂回します。 時間帯を変えると通ることがよくあります（日中より深夜のほうが混みやすい日もあります）。

ローカルで「モデルが見つからない」

Ollama が起動しているか（ollama list）を確認してください。 1 体も無いと起動を中断します。逆に 1 体でもあれば、その 1 体で動きます。

秘密のデータを扱うとき

クラウド構成では質問文と添付ファイルの本文が外部 API に送信されます。 機密を扱う場合はローカル構成（FUGU_BACKEND 未設定）を使ってください。 設計は同一なので、切り替えても使い方は変わりません。

Expectations

何に効いて、何に効かないか

使い始める前に知っておくと失望が少ない点を、実測にもとづいて挙げます。 詳しい根拠はトップページの実測結果と限界にあります。

効く

  • +答えが 1 つに定まる問題（数学・アルゴリズム・選択式）。投票が使える
  • +時間をかけてよい難問。単発 40% が合議で 97% に上がった実測がある
  • +コード生成。実行して確かめる経路がある
  • +夜間バッチ。待ち時間が問題にならない場面

効かない

  • −速さが要る用途。対話補完の代わりにはならない
  • −答えが定まらない創作・相談。投票が効かず、統合役の能力に頭打ちする
  • −平易な大量処理。1 問あたり数〜数十リクエストを使う
  • −全モデルが同じ誤読をする問題。票を増やしても直らない

この系の本質は「モデルを増幅する層」です

fugu 単体には性能がありません。同じモデル群を単発で呼ぶと約 40%、 同じモデル群をこのオーケストレーションに通すと 97%（AIME26 実測）。 差の 57 ポイントが設計の寄与です。 したがって手元のモデルが良くなれば、この層の出力もそのまま良くなります。

実測結果と限界 → 次期設計と訂正 → ロードマップ → アーキテクチャ → 計算量スケーリング →
